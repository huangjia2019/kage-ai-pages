四层结构：这套工作每一层各自在做什么

案例是参考资料。概念是认知基础。模式是通用语言。双轴矩阵是容器。

有读者问我应该先读哪一篇文章，或者书里哪一章是"主章"。诚实的答案是：没有任何一篇能单独站住。这套工作是有四层的，每一层做的事，其他三层替代不了。

我把它写下来，是因为我自己在决定下一步写什么的时候，反复在用这四层做划分，但一直没有把它们放在同一处。

四层

案例是参考资料。当我写一支 RegTech 团队怎么在成本封顶下搭出 RAG 流水线，或者一个客服 Agent 在模型中途被弃用时自动改道，案例是原始输入。它是发生过的事，不是论断本身。案例回答的是一个问题：工程师实际做了什么，什么超出了他们的预期？案例老得快——去年的案例可能在今年的模型上跑不动——但它的职责是让每一条主张都落在某件发生过的事情上。

概念是认知基础。概念是一种五年后应该仍然成立的主张。模型在花钱，Harness 在控预算。 没有坐标的模式名，是一个标签，不是一次设计决策。 当模型被锁死、成本是硬约束时，模式选型就是设计。这些不是目录条目。它们是关于 Agent 系统长什么样的承重主张。一个概念如果被证伪，它上面的所有结构都要重新审视一遍。代价高，所以我写得少，改得慢。

模式是通用语言。Prompt Chaining、Reflection、层级委派、守卫三明治——这些是词汇。它们的职责是让两个不同公司的工程师在不画一小时白板的前提下，确认他们说的是同一个设计。模式不是发现。它们里大多数在我命名之前就存在，我做的工作是命名和归位，不是发明。没有被采纳的词汇会死，被采纳的词汇会成为后续所有对话的基础设施。

矩阵是容器。双轴框架——认知功能 × 执行拓扑——是把以上三层装在一起的结构。它是让案例可被检索、概念可被索引、模式可被消歧的目录。没有它，这套工作是一堆散文；有了它，这套工作是一个可被导航的结构，任何新的模式、案例或概念都能落到一个坐标上，而矩阵里的空格会告诉你下一步应该写什么。

为什么哪一层都不能少

我见过四种缺失：

只有案例没有概念的书是一本战场故事集——读着有意思，读完什么都带不走。

只有概念没有案例的书是一本设计哲学——结构漂亮但无法被证伪。读者合上书觉得自己被说服，但周一早上不知道该做什么。

只有模式没有矩阵的书是当前大多数 Agent 文献的样子——一长串命名过的名词，两个工程师都说自己用 "Plan-and-Execute"，三个月后才发现他们做的是不兼容的系统。

只有矩阵没有模式、概念和案例的，是一张图。它出现在 conference slide 上，翻一页就被忘记。

四层是叠合的。案例生出概念。概念逼出模式。模式需要坐标。坐标构成矩阵。矩阵反过来告诉你哪些案例缺失、哪些概念还没被命名、哪些模式还没归位。

怎么用这套工作

如果你是一个本季度要把系统上线的工程师，案例是入口。找一个约束匹配你的。

如果你是一个要做"在当前模型之后还要成立"的决策的架构师，概念是入口。它是这套工作里不被模型版本拖垮的那一层。

如果你是一个要跨角色或跨组织对齐的团队，模式是入口。先把词汇给到所有人，剩下的会跟上。

如果你想理解整个领域，或者想找出领域里还没有人填的格子，矩阵是入口。空白格里住着下一个十年的工作。

每一层各自住在哪里

  • 案例——《Designing AI Agents》（Manning, 2026）的章节案例；本站案例区随后逐步充实。
  • 概念——本站 /zh/concepts/，每一篇都有一个固定 URL。
  • 模式——adpsagent.com/zh/patterns/ 的 33 篇白皮书，一格一篇；Manning 书一章一模式。
  • 矩阵——双轴框架，立场论文 arXiv:2605.13850；交互版本见 /zh/research/。

我把这篇文章既当作给读者的导览，也当作给自己的备忘录。每次坐下来想下一个章节、下一次演讲、下一篇文章，我都在问自己一句：这一篇在为哪一层服务？如果答不出来，这一篇就还没到能写的时刻。
